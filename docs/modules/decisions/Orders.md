# Orders 業務決策紀錄

> 業務規則的決定與理由。現況規則見 [Orders.md](../Orders.md)，格式見 [模組總覽「業務決策紀錄」](../README.md#4-業務決策紀錄)。

## DD-ORD-001：訂單明細（2026-11-16，使用者決定；CLAUDE.md §6「API 回應與 docs/api-conventions.md 的落差」）

- **背景**：下單成功時，回應的 Location 指向 `/api/orders/{id}`，但這個端點還沒做；「我的訂單」也點不進單一筆訂單。
- **決定**：
  - `GET /api/orders/{id}` 回傳與列表中每一筆相同的內容（`OrderDto`）。配送方式目前固定為 1、沒有選項，所以不回傳。
  - 不存在、不是自己的、已軟刪除的訂單都回 404，`general`：「找不到訂單」。不回 403，不讓人分辨訂單是否存在。
  - 明細依下單時送來的順序排列（明細 Id），列表一起改。
  - 前端明細頁 `/orders/:id`，需要登入：
    - 找不到時顯示「找不到這筆訂單」與「回我的訂單」按鈕。
    - 載入失敗時顯示「暫時看不到這筆訂單」與「重新載入」按鈕。
    - 網址的 Id 不是正整數時，不送請求。
  - 「我的訂單」的「訂單 #Id」做成連結，右側另放「查看明細」按鈕：只讓整張卡片可以點的話，鍵盤與報讀軟體不容易發現。
  - 結帳成功後提示「訂單已送出」，導向新訂單的明細頁。
  - 訂單時間固定以台灣時間（Asia/Taipei）顯示，格式為 `2026/11/16 14:05`，不跟著瀏覽器的時區與地區格式。
  - 明細頁的品名連到商品頁，作為之後「再買一次」的入口。商品下架時，商品頁會顯示「找不到這項商品」。
- **放棄的東西**：列表和明細回傳一樣的資料，列表的回應沒有變小。日後明細頁需要列表沒有的欄位時，要另外開 DTO。
- **未做**：
  - 「我的訂單」與結帳頁整頁遷移到 UI 規範（CLAUDE.md §6「前端 feature 頁面遷移到 UI 規範」）。
  - 訂單狀態與取消。
- **驗證**：
  - `GetOrderDetailHandlerTests`：自己的、別人的、不存在的訂單。
  - 用 API 查別人的訂單 Id，回 404。

## DD-ORD-002：庫存與扣庫存（2026-11-18，使用者決定；CLAUDE.md §6「庫存欄位與扣庫存交易」）

- **背景**：商品沒有庫存欄位，任何商品都能下單，數量也沒有限制（只有每項 99 件）。
- **決定**：
  - `products.stock` 是庫存件數，0 表示售完。商品 API（列表、明細、相關商品、搜尋）都回傳精確的件數 `stock`，
    前端才能把數量上限設成剩下的件數。
  - 下單時檢查順序：欄位（400）→ 商品是否存在（400）→ 庫存（409）。409 等欄位都通過才檢查，因為庫存是資料的狀態、不是輸入格式。
  - 庫存不足回 409，`items`：「下列商品庫存不足：{品名}（剩 N 件）、{品名}（已售完）」。列品名不列 Id，使用者才知道要改哪一項。
  - 扣庫存與建立訂單在同一個交易內，任何一項扣不到，整筆訂單不成立（不做「有貨的先出」）。
  - 既有商品在導入時一律設成 100 件：既有環境照舊可以下單，一筆訂單最多 99 件，一筆就買不完。
  - 售完的商品照常列出，不隱藏、不排到最後；列表與搜尋的按鈕顯示「已售完」並停用。
  - 明細頁：售完顯示「已售完」，輸入框與按鈕停用；1–5 件顯示「僅剩 N 件」；超過 5 件不顯示數字。
    數量上限是庫存與 99 取小的。
  - 加入購物車時，同一項商品的合計超過上限就調整成上限，並提示「庫存只剩 N 件，購物車已調整為 N 件」；成功時提示「已加入購物車」。
  - 購物車頁不知道庫存，「＋」照舊只限 99 件；結帳收到 409 時顯示後端的訊息與「回購物車調整數量」連結，不自動修改購物車。
- **放棄的東西**：
  - 庫存數字對外公開，任何人都查得到每項商品還剩幾件。
  - 購物車裡的數量可能已經超過庫存，要到送出訂單才知道。
  - 一項缺貨就整筆不成立，使用者要自己刪掉那一項再送。
- **未做**：
  - 取消訂單回補庫存（訂單狀態與取消的 Pull Request）。
  - 購物車與現價、庫存同步（CLAUDE.md §6「購物車價格與現價不同步」）。
  - 調整庫存的 API、到貨通知、首頁卡片的售完標示。
- **驗證**：
  - `CreateOrderHandlerTests`：庫存不足、售完、剛好足夠、同商品分多筆、檢查後被買走、扣庫存順序、欄位錯誤優先。
  - 對本機 API 同時送 10 筆各 1 件的訂單到庫存 5 的商品：5 筆 201、5 筆 409，庫存變 0。
