## DD-ORD-001：訂單明細（2026-11-16，使用者決定；CLAUDE.md §6「API 回應與 docs/api-conventions.md 的落差」）

- **背景**：下單成功時，回應的 Location 指向 `/api/orders/{id}`，但這個端點還沒做；「我的訂單」也點不進單一筆訂單。
- **決定**：
  - `GET /api/orders/{id}` 回傳與列表中每一筆相同的內容（`OrderDto`）。配送方式目前固定為 1、沒有選項，所以不回傳。
  - 不存在、不是自己的、已軟刪除的訂單都回 404，`general`：「找不到訂單」。不回 403，不讓人分辨訂單是否存在。
  - 明細依下單時送來的順序排列（明細 Id），列表一起改。
  - 前端明細頁 `/orders/:id`，需要登入：
    - 找不到時顯示「找不到這筆訂單」與「回我的訂單」按鈕。
    - 載入失敗時顯示「暫時看不到這筆訂單」與「重新載入」按鈕。
    - 網址的 Id 不是正整數時，不送請求。
  - 「我的訂單」的「訂單 #Id」做成連結，右側另放「查看明細」按鈕：只讓整張卡片可以點的話，鍵盤與報讀軟體不容易發現。
  - 結帳成功後提示「訂單已送出」，導向新訂單的明細頁。
  - 訂單時間固定以台灣時間（Asia/Taipei）顯示，格式為 `2026/11/16 14:05`，不跟著瀏覽器的時區與地區格式。
  - 明細頁的品名連到商品頁，作為之後「再買一次」的入口。商品下架時，商品頁會顯示「找不到這項商品」。
- **放棄的東西**：列表和明細回傳一樣的資料，列表的回應沒有變小。日後明細頁需要列表沒有的欄位時，要另外開 DTO。
- **未做**：
  - 「我的訂單」與結帳頁整頁遷移到 UI 規範（CLAUDE.md §6「前端 feature 頁面遷移到 UI 規範」）。
  - 訂單狀態與取消。
- **驗證**：
  - `GetOrderDetailHandlerTests`：自己的、別人的、不存在的訂單。
  - 用 API 查別人的訂單 Id，回 404。
