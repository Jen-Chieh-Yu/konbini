Ready · 現有的 API 就做得到

  • Email ＋ 密碼登入 — POST /api/auth/login 收 {email, password}，回 {token, user}。
  • 登入中狀態 — LoginView.vue 已有 submitting 與 :loading。
  • 登入失敗訊息 — 已在讀 e.response?.data?.errors?.general，草稿只是把它從 ElMessage 改成表單上方的 alert。錯誤訊息刻意不區分「帳號不存在」與「密碼錯誤」，避免洩漏哪些 Email 有註冊。
  • 前端欄位驗證 — 換成 el-form 的 rules 就有，ui-guidelines 要求錯誤要指到具體欄位。目前 LoginView 沒有 rules。
  • 註冊入口 — /register 路由已存在。
  • 顯示密碼 — el-input 的 show-password，LoginView 已經在用。

Blocked · 後端沒有的功能

  • 忘記密碼 — 沒有重設密碼的 API。PUT /api/auth/password 有 .RequireAuthorization()，是「已登入後改密碼」，不能拿來重設。要做的話需要寄信、產一次性 token、驗證，是一整條流程。草稿裡這個連結標成紅色。
  • 保持登入狀態 — token 現在直接存在 localStorage，等於永遠保持登入，沒有過期也沒有 refresh token。這個勾選框現在沒有意義，除非先決定 token 的生命週期。
  • 訪客結帳 — 後端沒有。
  • 第三方登入（Google／LINE）— 草稿已經把按鈕畫進去，但後端完全沒有 OAuth。要做需要：註冊各家的 OAuth 應用、後端加 callback 端點、User 加上外部識別欄位（provider ＋ 對應的使用者 id），還要處理「同一個 Email 已用密碼註冊過」的帳號合併。工程量比看起來大。
  • Email 驗證 — 註冊後沒有驗證信，等於任何 Email 都能註冊。

Security · 一件跟版面無關但該記著的事

AuthEndpoints.cs 的註解已經寫明登入沒有速率限制，並標為「若日後對外開放，這是上線前必補項」。既然現在在做登入畫面，順便提一下：這頁做得再好，沒有速率限制的登入端點就是可以被暴力破解的。純練習專案不上線的話沒問題，只是別忘了那條註解。

Layout

為什麼是左右兩欄

做法說明
左註冊／右登入把新客人放在視線起點，登入放右邊。日本 EC 兩種排法都常見（KALDI、成城石井是登入在左）；這版選擇讓第一次來的人先看到註冊的理由，代價是回頭客每次都要往右找。回頭客佔多數的話，這個取捨要重新評估。
右欄列出註冊好處只放一顆「註冊」按鈕的轉換率低。三點寫的是這個站實際有的功能，不是空泛的「享有會員優惠」。
手機版堆疊820px 以下改單欄，用 CSS order 把登入拉到最上面、註冊在下——手機上多半是回頭客。
錯誤訊息放表單上方目前是 ElMessage 快顯，會自己消失。登入失敗需要停留在畫面上，讓人能對照著改。欄位層級的錯誤另外指到欄位。
輸入框 48px、按鈕 52px跟商品頁的數量選擇器同一組尺寸，手機上不會誤觸。

Notes

下一步

  • 註冊頁還沒畫。RegisterView.vue 目前是原生 <form>／<input>，完全沒有用 Element Plus，跟其他頁不一致。而且欄位不少（姓、名、Email、密碼、確認密碼、手機、生日三個下拉），要排版才會好用。
  • 登入後導向哪裡目前寫死回首頁。從商品頁點登入的人，登入後應該回到原本那頁——這要在路由上帶 redirect 參數。
  • 結帳流程中的登入還沒想過。如果結帳一定要登入，那從購物車進登入頁的動線要跟這頁不一樣（要保留購物車內容）。
