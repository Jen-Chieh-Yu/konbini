Ready · 現有的 API 就做得到

  • 訂單編號 — POST /api/orders 成功時回 orderId，放進路由參數，重新整理也還在。
  • 收件資訊與商品（快照） — 送出前把表單與購物車內容存在 store，完成頁讀出後清掉；重新整理後快照不在，退回只顯示編號（REFRESHED）。
  • 合計 — 快照的金額是前端算的；後端重新計價後可能不同，所以快照版本旁邊不標「實付金額」。

Blocked · 後端沒有的功能

  • 訂單明細 API — 沒有 GET /api/orders/{id}（CLAUDE.md §6「API 回應與規範的落差」：下單回的 Location 也指向這個還不存在的端點）。有了它，完成頁就不需要快照，金額也一定是後端算的。
  • 訂單確認信 — Email 驗證上線後才有寄信機制（Mailpit＋IEmailSender），屆時可以順便寄訂單確認信。
  • 付款 — 沒有付款流程，畫面上的「貨到付款」只是說明現況。

Reference

與參考網站的區塊對照

只記錄版型結構與資訊密度的觀察，不沿用任何網站的配色、圖示、文案與素材；細節實作前以實際網站為準。

參考網站的做法Konbini調整理由
雜貨電商常見：完成頁顯示訂單編號，並提示確認信已寄出大字訂單編號＋確認信提示客服問題第一句通常是「訂單編號多少」；確認信要等寄信機制，先標為後端未支援。
家樂福線上購物：完成頁重述配送與付款資訊收件資訊卡片貨到付款要讓人知道「送到時要準備現金」，在完成頁再講一次。
Instacart：完成後引導到訂單狀態頁查看我的訂單／繼續購物沒有即時配送狀態，所以只連到訂單列表；主要按鈕給「繼續購物」。

Layout

為什麼這樣排

做法說明
新增完成頁，不再直接跳 /orders現在送出後直接到訂單列表，使用者要自己找剛下的那一筆；完成頁明確告訴他「成功了、編號是多少」。
單欄 640px 置中內容是一份收據，不需要兩欄；比表單頁（480px）寬一點，放得下商品列的金額。
步驟條全部打勾與結帳頁同一個元件，讓流程有結尾。
