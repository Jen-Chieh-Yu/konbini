# 發行流程

半自動發行：**CI 產出並驗證成品，部署由人執行**（決策與理由見 `CLAUDE.md` §6「半自動發行」）。
部署步驟見 [部署手冊](deployment.md)。

## 1. 版號規則

依 [語意化版本](https://semver.org/lang/zh-TW/)：`主版本.次版本.修訂號`。

| 位置 | 什麼時候 +1 | 例子 |
| --- | --- | --- |
| 主版本 | 破壞相容：移除或改名 API 路由、欄位，改設定鍵、環境變數，資料庫需要人工處理 | `0.4.2 → 1.0.0` |
| 次版本 | 新增功能，向下相容 | `0.4.2 → 0.5.0` |
| 修訂號 | 只修缺陷 | `0.5.0 → 0.5.1` |

- 往前面的位數進位時，後面歸零：`0.4.2` 加新功能是 `0.5.0`。
- **目前是 `0.x`**：代表還在發展、不保證相容（本專案不正式上線）。`1.0.0` 留給真的要上線的那天。
- 預覽版加字尾：`v0.2.0-rc.1`。Release 會自動標成 pre-release。
- git 標籤與 Release 用 `v0.1.0`；映像標籤、`APP_VERSION`、`/api/version` 用 `0.1.0`（CI 會去掉 `v`）。

**版號跳動的時機是發行，不是 commit**：合併 Pull Request 不跳版號、不打標籤。

## 2. 發行步驟

順序不能顛倒——**先合併變更紀錄，再打標籤**，標籤指向的 commit 才包含這一版的說明。

1. **確認 main 是綠燈**：Actions 頁面 main 最新一次 CI 全部通過。
2. **整理 `CHANGELOG.md`**：用 main 的歷史產生草稿（Squash 後一個 commit 就是一個 Pull Request）：

   ```bash
   git log <上一個標籤>..origin/main --first-parent --pretty='- %s'
   ```

   第一次發行沒有上一個標籤，改成盤點系統現況。草稿要人工修：刪掉過程性的項目（`ci:`、`chore:` 通常不收），
   改寫成完整句子、拿掉 `feat:` 這類前綴、放進正確分類。`[未發行]` 改成 `[x.y.z] - YYYY-MM-DD`，上面補一個空的 `[未發行]`。
   檔案最底部的連結一併更新：`[未發行]` 改為比較 `vX.Y.Z...HEAD`，並新增 `[x.y.z]` 指向該版的 Release。
3. **用 Pull Request 合併變更紀錄**：分支 `docs/YYYYMMDD-release-vX.Y.Z`，title `docs: 更新 vX.Y.Z 變更紀錄`。
4. **在 main 打 annotated 標籤並推送**：

   ```bash
   git switch main && git pull --ff-only
   git tag -a v0.1.0 -m "v0.1.0：首次發行"
   git push origin v0.1.0
   ```

   一律用 `-a`：會記錄誰在什麼時候決定發這一版。
5. **等 CI 跑完**（約 10–15 分鐘）：
   - 打包：決定版號——檢查版號格式，以及**標籤是否在 main 上**（不在就失敗、不產出任何成品）
   - 打包：映像與冒煙測試（amd64、arm64）——用剛建好的映像跑部署佈局，確認 api、postgres、mailpit 健康、client 執行中、首頁與 `/api` 可用、版號正確
   - 發行：建立 Release 草稿——附上兩種架構的映像檔
6. **檢查 Release 草稿**：Releases 頁面 → 草稿 → 確認附件有 4 個檔案（api、client × amd64、arm64），
   說明可以貼上 `CHANGELOG.md` 這一版的內容 → **Publish release**。
7. **部署**：照 [部署手冊](deployment.md)。

## 3. 在分支上測試打包（不是發行）

改了 `ci.yml`、Dockerfile、compose 等會影響打包的東西，合併前想先確認：**不要在分支上打 `v*` 標籤**
（已推送的標籤原則上不刪，會跟正式版號混在一起）。改用手動執行：

1. Actions → 左欄 **CI** → 右上 **Run workflow**
2. 選要測試的分支，勾選 **測試打包**，按 **Run workflow**
3. 版號為 `0.0.0-test.<執行編號>`，成品名稱為 `konbini-images-test-<執行編號>-<架構>`，保留 7 天

測試打包和正式發行跑同一套驗證（含冒煙測試），差別只在版號、不建立 Release。**測試成品只能用於測試。**

## 4. 出錯時

| 狀況 | 處理 |
| --- | --- |
| 版號格式錯（例：`v1.2`）或標籤不在 main 上 | CI 在「決定版號」就失敗，沒有任何成品。這種標籤可以刪除後重打：`git push --delete origin v1.2`、`git tag -d v1.2` |
| 冒煙測試失敗 | 看該 job 的「印出容器日誌」步驟。修正後發**下一個修訂版**（`v0.1.1`），不要移動或重打已推送的標籤 |
| Release 草稿內容有誤 | 草稿可以直接在網頁編輯；附件有誤就刪掉草稿，從 Actions 該次執行的 Artifacts 重新上傳 |
| 已發布的版本有問題 | 不刪標籤、不刪 Release，發修訂版修正；部署端照部署手冊「回到上一版」處理 |
